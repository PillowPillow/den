# Real smoke #3 — `den build` end to end: `stop`, `template save`, the closed loop (2026-08-03)

Third run of the assembled binary against a **real `sbx`** (v0.35.0, `/opt/homebrew/bin/sbx`, build
`01e01520456e4126a9653471e7072e4d9b280321`), on macOS 25.5.0. Answers issue #31, which blocks #10.

**Language.** English, matching its sibling `2026-07-31-smoke-reel-2.md`. CLAUDE.md says handoffs
under `docs/superpowers/` are French; the smoke handoffs are not, and this one follows the file next
to it rather than reopening that question here.

**Bench.** `DEN_HOME` in a scratchpad, one throwaway agent profile, three throwaway stacks, one nest
with no repos. No repository of the user's was mounted at any point. Binary: `go build -o den
./cmd/den` at **`4ee021f`** (version stays `dev` — issue #10).

**Baseline, 17:04.** `sbx ls --json` → `{"sandboxes":[]}`. `sbx template ls --json` → four images
(`docker/sandbox-templates:claude-code-docker` `9a3bab17aae9`, `:shell-docker` `39cf20eca861`,
`library/devx:v1` `11a2e5ef4234`, `library/dgdevx:v1` `ed6a22e522cc`). `sbx policy ls` → one row,
`local-policy`. The image name used throughout, `den-smoke3:v1`, was **verified absent** from that
list before anything was created — the overwrite test of §3.3 below is destructive by design and was
aimed only at a name this smoke owns.

**Final state, 17:16.** `sbx ls --json` → `{"sandboxes":[]}`. `sbx template ls --json` → the same
four images, **same ids**. `sbx policy ls` → one row, `local-policy`.

Eleven build VMs and one spawned sandbox were created over the run, and **every one of them is
gone** — the ones den tore down itself (including `slow-build`, killed mid-step, and every
`*-build` of a stack that failed), the hand-made `smoke3-build` of §8.3 removed with the very
command den's refusal quotes, and `probe` destroyed with `den rm`. Three images were created —
`den-smoke3:v1`, `den-smoke3-child:v1`, `den-smoke3-t2:v1` — and all three removed with `sbx
template rm`. Two more never existed at all, and that is the point of the sections that produced
them: `den-smoke3-slow:v1` (interrupted before the `save`, §8.2) and `den-smoke3-midfail:v1` (step 2
of 3 failed, §8.0). **No pre-existing image or sandbox of the user's was touched.**

## 2. The argv that discriminates everything — measured before a single VM

```
$ sbx template save --help
Usage:
  sbx template save SANDBOX TAG [flags]

Examples:
  sbx template save my-sandbox myimage:v1.0
  sbx template save my-sandbox myimage:v1.0 --output /tmp/myimage.tar

Flags:
  -o, --output string   Also export the image to a tar file

$ sbx stop --help
Usage:
  sbx stop SANDBOX [SANDBOX...]
```

**`save SANDBOX TAG`, positional, no `--tag` and no `-t`.** `internal/build/execute.go:305` sends
exactly that. `stop SANDBOX`, positional, variadic; `execute.go:299` sends the single-name form.

This was run first, deliberately: if the form had differed, den could not build anything and this
task would have become "file a bug and fix the argv" rather than "measure".

## 3. `sbx stop` and `sbx template save` in isolation

Measured on a live sandbox spawned by `den probe` (§5), not on a build VM, so that each answer is
attributable to one command rather than to a sequence.

### 3.1 `stop` on a running sandbox, then on an already-stopped one

```
$ sbx stop probe
Sandbox 'probe' stopped
rc=0

$ sbx stop probe          # replayed immediately, sandbox already stopped
Sandbox 'probe' stopped
rc=0
```

**A second `stop` is a no-op, not a refusal** — same message, same exit code, and `sbx ls --json`
keeps reporting `"status":"stopped"`. This is the property `buildOne`'s deferred teardown needs: the
happy path stops the VM before saving and the teardown then runs `rm --force` over an already-stopped
sandbox, while an interrupted build reaches the teardown without a preceding `stop`. Both orders are
legal.

### 3.2 `save` on a sandbox that is still running — the reason the order is the order

```
$ sbx template save probe den-smoke3-t2:v1
Sandbox probe is running and must be stopped before saving. Stop it now? (y/N): ERROR: cannot save a running sandbox; stop it first with: sbx stop probe
rc=1
```

**`save` refuses a running sandbox, and it refuses by first asking an interactive question.** With no
tty the prompt read nothing, fell through, and the command exited 1.

Issue #31 asked whether the `stop` before `save` was really required or merely tidy. It is required,
and more strongly than the question assumed: without it den would not get a clean error, it would put
a **`(y/N)` prompt** into a non-interactive build. `den build` streams a step's output through
`sbx.Exec.Stream`, whose sink is a writer and not a tty, so the prompt would be answered by nothing
and the build would fail late with a message about a running sandbox — after every provisioning step
had already run. §6's order is load-bearing.

### 3.3 Replaying `save` over an existing image

```
$ sbx template save probe den-smoke3-t2:v1     # sandbox now stopped
Snapshotting image in sandbox ...
Save complete. To use the image as a template:
    sbx run -t docker.io/library/den-smoke3-t2:v1 AGENT [WORKSPACE]
rc=0
→ docker.io/library/den-smoke3-t2:v1 id=d10919141c13

$ sbx template save probe den-smoke3-t2:v1     # same name, replayed
Snapshotting image in sandbox ...
Save complete. ...
rc=0
→ docker.io/library/den-smoke3-t2:v1 id=e4054ac53a4c
```

**Silent success, rc=0, and a NEW id.** No refusal, no prompt, no `--force` of its own. The previous
id disappears from `template ls --json` entirely — it is not listed as untagged, it is simply gone
from that view.

Consequence for den: **`--force` does not need a `template rm` first.** `execute.go` is right to
`save` straight over the name. The cost is that each rebuild leaves the previous layers behind
where `sbx template ls` does not show them; den is not the surface that reclaims them and this smoke
does not propose that it become one.

## 4. `den build` end to end on a root stack

Stack `smoke3`: no `parent:`, `base: claude`, `image: den-smoke3:v1`, one `provision.includes`
(`common.sh`, defining `SMOKE_MARKER`) and two `provision.steps` — step 1 runs a real
`apt-get update && apt-get install -y tree`, step 2 writes a marker and calls `tree --version`.

```
$ den build smoke3
[1/1] smoke3: building den-smoke3:v1...
... (apt output, live — see §7) ...
Setting up tree (2.3.1-1) ...
built by den smoke3 at step 2
tree v2.3.1 (c) 1996 - 2026 by Steve Baker, ...
rc=0
```

**23 seconds, exit 0.** The full sequence den owns — `create` → 2 × `exec` → `stop` → `template
save` → `rm` — ran against a real `sbx` for the first time. The two links issue #31 was opened for,
`stop` and `template save`, both answered.

`includes` worked as specified: `SMOKE_MARKER` is defined in `common.sh` and consumed in step 2,
across two separate `sbx exec` invocations, which is exactly the case that exists because nothing but
the VM filesystem survives between steps.

### 4.1 The pairing check — how a bare reference is completed

The stack declares `image: den-smoke3:v1`, **bare**: no registry, no namespace.

```
$ sbx template ls --json
  ...
  docker.io/library/den-smoke3:v1   id=18b13680ead7   flavor=claude-code-docker
```

**`save` completes a bare reference to `docker.io/library/…`, the same way `ls` reports it.**
`sbx.NormalizeImageRef` assumed exactly this, and the assumption holds. Confirmed twice
independently: `template ls --json` reports the qualified form, and `save`'s own success line echoes
back `sbx run -t docker.io/library/den-smoke3-t2:v1`.

This is the measurement #8's open loop depended on. If the two sides had completed differently,
`den build` would have succeeded and `den <nest>` would have kept demanding a build forever.

The flavor is **inherited from the base**, `claude-code-docker`, not recomputed.

## 6. Parent chain and `--force`

Stack `child`: `parent: smoke3`, `image: den-smoke3-child:v1`, one step whose **first line is `tree
--version`** — a binary that exists only in the parent's image, so a wrong `--template` edge fails
the step rather than passing quietly.

```
$ den build child
[1/2] smoke3: skipped, image den-smoke3:v1 already built (--force rebuilds it)
[2/2] child: building den-smoke3-child:v1...
tree v2.3.1 ...
child layer
rc=0
```

Ancestor present → skipped, and the skip line names the flag that would change it. The child built
**from the parent's image**.

```
$ den build child --force
before: den-smoke3:v1 18b13680ead7   den-smoke3-child:v1 eb8bca3fd2f6
[1/2] smoke3: building den-smoke3:v1...
[2/2] child: building den-smoke3-child:v1...
rc=0
after:  den-smoke3:v1 eb6e3574a9ad   den-smoke3-child:v1 90fa39fd8f3e
```

**Both ids changed**: `--force` rebuilt the ancestor too, and the child was rebuilt on top of the new
parent rather than the stale one. 37 seconds.

## 7. Live streaming — measured, and not on the stream you would guess

Stack `slow`: one step emitting `tick N on stdout` and `tick N on stderr` once a second for 60
seconds. `den build slow` was backgrounded with stdout and stderr redirected to two separate files,
which were sampled while it ran.

| sample | den's stdout | den's stderr |
|---|---|---|
| t+15s | 3 lines | 0 |
| t+20s | 13 lines | 0 |
| t+25s | 23 lines | 0 |

**Output arrives during the step, at the step's own rate.** Not buffered to the end. This is what
`58e453e` claims and it holds against a real `sbx`.

**And both of the step's streams land on den's STDOUT.** `tick N on stderr` appears in den's stdout,
interleaved with `tick N on stdout`; den's stderr stayed empty until the final diagnostic. This is
deliberate — `sbx.Exec.Stream` wires `cmd.Stdout` and `cmd.Stderr` to **one** `streamSink`, and
`execute.go` hands it `out`. Recorded because the natural reading of "a step's stderr reaches the
user" is "on stderr", and it does not: it reaches them on stdout, live, in order. The separation den
does keep is between the step's log (`out`) and den's own diagnostics (`errOut`), and that one was
confirmed by every failure below.

## 7bis. `den build` with no argument — the fan-out over every declared stack

`build --help` says "Without an argument, every declared stack is built", and that is a different
code path from `den build <stack>`. Measured with four stacks declared (`smoke3`, `child` whose
`parent:` is `smoke3`, `slow`, `midfail`), starting from **no** smoke3 image at all.

```
$ den build
[1/4] smoke3: building den-smoke3:v1...
[2/4] child: building den-smoke3-child:v1...
[3/4] midfail: building den-smoke3-midfail:v1...
den: stack "midfail": step 2/3 /…/midfail/provision/02-boom.sh failed: exit status 1
rc=1
```

Three things at once:

- the counter spans **all four** declared stacks, not the chain of one;
- **parent order is honoured across the fan-out** — `smoke3` was built at `[1/4]` and `child`, which
  derives from it, at `[2/4]`. The ordering is not an artifact of `den build <child>` walking one
  chain;
- **the fan-out is fail-fast, not best-effort.** `midfail` failed at `[3/4]` and `slow` at `[4/4]`
  **never ran**. The two stacks already built kept their images (`den-smoke3:v1` `0b8422c4ebc2`,
  `den-smoke3-child:v1` `11dca3ce9dcb`) — a failing stack does not roll back its predecessors — and
  `sbx ls --json` was `{"sandboxes":[]}` afterwards, so `midfail`'s own build VM was still torn down.

## 8. The failure paths

### 8.0 A deliberate failure at a MIDDLE step — step 2 of 3

Stack `midfail`: three steps, step 1 prints and succeeds, step 2 prints then `exit 1`, step 3 must
never run. This is the case issue #31 names, and it is the one that discriminates a real step counter
from one that would always read `1/N`.

```
stdout:  [1/1] midfail: building den-smoke3-midfail:v1...
         STEP ONE RAN AND SUCCEEDED
         STEP TWO IS ABOUT TO FAIL ON PURPOSE
stderr:  den: stack "midfail": step 2/3 /…/midfail/provision/02-boom.sh failed: exit status 1
rc=1
```

**`step 2/3`** — the index is the failing step's, the total is the stack's. Step 1's output sits
above the error and step 3's line is absent, so the sequence stopped at the failure rather than
running on. Absolute path, `exit status 1`, no argv. `sbx ls --json` → `{"sandboxes":[]}`: no
`midfail-build`, and no `den-smoke3-midfail:v1` image, since the save is downstream of the steps.

### 8.1 A step that fails at the FIRST step

Measured **accidentally and genuinely** on the first run of §4, before the step was made to wait for
the apt lock: the build VM plays its own `apt-get` at startup and step 1 raced it.

```
stdout:  [1/1] smoke3: building den-smoke3:v1...
         Reading package lists...
         E: Could not get lock /var/lib/apt/lists/lock. It is held by process 301 (apt-get)
         E: Unable to lock directory /var/lib/apt/lists/
stderr:  den: stack "smoke3": step 1/2 /…/bench/stacks/smoke3/provision/01-tree.sh failed: exit status 100
rc=1
```

Kept because it is a *different* failure from §8.0 — an unplanned one, from the tool rather than from
a script written to fail — and it confirms the same four properties:

- the shape is **spec §6's exactly**, `stack "S": step N/M <path> failed: exit status K`, **no argv**;
- the path is **absolute** — issue #30's arbitration verified against reality, not against a golden;
- the step's log sits **above** the error, on the other stream;
- **no residue**: `sbx ls --json` → `{"sandboxes":[]}` and no `den-smoke3` image.

On its own it would not have been enough: a failure at step 1 cannot distinguish a correct step
counter from one hardcoded to `1`. §8.0 is what settles that.

The finding worth carrying forward for anyone writing a stack: **a `provision.steps` entry that calls
`apt-get` immediately races the build VM's own startup apt-get.** The step must wait for the lock.
That is a property of the base image, not of den, and den reports it correctly rather than papering
over it.

### 8.2 `^C` in the middle of a step

`den build slow` was interrupted with `kill -INT` at t+30s, mid-step-1-of-2.

```
stderr:  den: stack "slow": step 1/2 /…/bench/stacks/slow/provision/01-slow.sh failed: interrupted (canceled): signal: killed
rc=1
```

**Reads as an interruption, not a crash**, and `interrupted (canceled)` names the cause before the
signal. Step 2 never ran. **7 seconds elapsed between the signal and den's exit** — the teardown ran
on a context that was already canceled (`37c607d`) — and `sbx ls --json` afterwards showed no
`slow-build`. No image `den-smoke3-slow:v1` was ever created.

This is the one check the hermetic suite proves only in shape (`05832df`); it is now measured.

### 8.3 A pre-existing `<stack>-build`

A sandbox named `smoke3-build` was created by hand with `sbx create`, then:

```
$ den build smoke3
stderr: den: stack "smoke3": a sandbox named smoke3-build already exists — den will not remove it
        for you, because that name is also a legal nest name. Inspect it, then `sbx rm --force smoke3-build`
rc=1
```

**Refusal, not a blind cleanup**, and nothing was printed on stdout — the build never started, so the
check fires before the first side effect. The remedy is a copy-pasteable command.

## 9. Active governance — still open

```
$ sbx policy check network deb.debian.org --json
{
  "action": "net:connect:tcp",
  "allowed": true,
  "context": "global",
  "governance": { "active": false },
  ...
}
```

`sbx policy check network` takes a **host argument** (`accepts 1 arg(s), received 0` without one) —
noted because §14.0 lists the command without it.

`governance.active` is **false** on this bench, as it was for the 2026-08-03 egress probe. **What a
build VM without a kit gets when governance is active remains unmeasured.** Written open, exactly as
issue #31 instructs: no active-governance bench exists here, and the absence of a bench does not
close a question. The decision it gates — whether the build VM needs an egress kit of its own, and
whether a stack's `egress:` (declared for its *spawns*) is the right list for its *build* — is
untouched by this smoke.

While `probe` was live, `sbx policy ls` did show a second row, `kit / sandbox:probe / network: 1
allow` — den's generated mixin, scoped to the sandbox, and it disappeared with `den rm`.

## What this closes and what it does not

**Closes #31, and unblocks #10.** The two links that produce the image, `sbx stop` and `sbx template
save`, have now answered a real binary: their argv is the one `execute.go` sends, their behaviour on
the edge cases den relies on (stop-when-stopped, save-when-running, save-over-an-existing-name) is
the behaviour den assumes, and the completion of a bare image reference matches on both sides so the
`build` → `spawn` loop actually closes.

**Does not close** the active-governance question of §6/§5 above. It stays open with no bench.

**Does not re-play** `den ports`, `-i`, `--agent` or interactive `den sh` — smoke #2 (#9,
`2026-07-31-smoke-reel-2.md`) covered them and nothing since has touched those paths. Nothing here
judges `den agent` / `den review`, out of v1 scope (spec §1).
