# Real smoke #4 — what a fresh sandbox has at `/home/agent/.ssh` (2026-08-10)

Fourth run against a **real `sbx`**, and the first one against **v0.37.1**
(`/opt/homebrew/bin/sbx`, `sbx version: v0.37.1 2d4f32448c7a94d7fa525517dfca21aa36599829`), on
macOS 25.5.0. Answers issue **#57**.

**Language.** English, matching its siblings `2026-07-31-smoke-reel-2.md` and
`2026-08-03-smoke-reel-3.md`. CLAUDE.md says handoffs under `docs/superpowers/` are French; the
smoke handoffs are not, and this one follows the files next to it rather than reopening that
question.

**Scope.** One question, and deliberately only one: **what does `/home/agent/.ssh` contain in a
freshly created sandbox?** Everything below exists to answer it and to prove the answer end to end.
Nothing else in spec §14.0 is re-attested — see "What this smoke does NOT say" at the bottom.

## Why the question mattered

`ssh.mode: mount` desugars into a `mounts:` entry linking `ssh.dir` to `$HOME/.ssh`, and the link
phase that runs in the VM is fail-closed (`internal/agent/links.go`, spec §10.1): a **non-empty**
directory at the link target is a refusal, by design. So if the base image shipped a seeded
`known_hosts`, an empty `authorized_keys` or a default `config`, **every `ssh.mode: mount` spawn
would die at boot**. The premise had never been measured — the code review of #55 rated it
PLAUSIBLE, not CONFIRMED, and skipped it for that reason.

## Bench

`DEN_HOME` in a scratchpad, one throwaway agent profile (`update: "true"`, so the freshness command
cannot mask a link-phase failure), one throwaway stack, one nest pointing at a throwaway git repo.
**No repository of the user's was mounted at any point**, and the two live sandboxes on the machine
(`dg-op-inscription`, `swimspot`) were never entered — not even read-only. Binary: `task build` at
`ac7b61b`.

## 1. The direct measurement — `ls -A` on four images

A throwaway sandbox per image, `sbx exec … ls -A /home/agent`, then `sbx rm --force`.

| image | flavor | `/home/agent/.ssh` |
|---|---|---|
| `docker/sandbox-templates:shell-docker` | stock | **absent** |
| `docker/sandbox-templates:claude-code-docker` | stock | **absent** |
| `devx:v1` | derived (built here) | **absent** |
| `godev:v1` | derived (built here) | **absent** |

What `/home/agent` does hold, for the record:

```
shell-docker        .bash_profile .bashrc .docker .gitconfig .gitignore_global .local workspace
claude-code-docker  .bashrc .cache .claude .claude.json .docker .gitconfig .gitignore_global .local .npm workspace
```

## 2. The permission half — the real gate is `rmdir`, not emptiness

`linkFunc` removes an existing directory with `rmdir`, which needs write permission on the
**parent**. An empty-but-root-owned `.ssh`, or a non-writable `/home/agent`, would produce the same
FATAL as a non-empty one. Measured, identical on all four images:

```
id            uid=1000(agent) gid=1000(agent) groups=1000(agent),27(sudo),1001(docker)
ls -ld /home/agent    drwxr-xr-x 1 agent agent
$HOME         /home/agent
```

So the parent is owned and writable by the very user the link phase runs as. The gate is open on
both counts, not just on emptiness.

## 3. End to end — a real `den spawn`, not a hand replay

`ls` is only the input to the gate. The gate itself was exercised by a real
`den spawn probe --detach` on the scratch `DEN_HOME`, with `ssh: {mode: mount, dir: <scratch>/ssh}`
and the stock `shell-docker` image. It booted. `/var/log/sbx-kit-startup.log`:

```
=== dispatcher run 2026-08-10T09:19:20Z ===
> /etc/durable-startup.d/001-startup-shell/000-cmd.sh
ok /etc/durable-startup.d/001-startup-shell/000-cmd.sh
> /etc/durable-startup.d/002-startup-den-probe/000-cmd.sh
den mounts: linking 1 mount(s)
den mounts: /home/agent/.ssh -> /private/tmp/.../probe57/denhome/ssh
ok /etc/durable-startup.d/002-startup-den-probe/000-cmd.sh
> /etc/durable-startup.d/002-startup-den-probe/001-cmd.sh
agent probe: up to date
ok /etc/durable-startup.d/002-startup-den-probe/001-cmd.sh
=== dispatcher complete ===
```

and in the VM:

```
lrwxrwxrwx+ 1 agent agent  /home/agent/.ssh -> /private/tmp/.../probe57/denhome/ssh
known_hosts
```

Three things fall out of that one run, and none of them is an inference:

1. **The link phase succeeds under the real dispatcher**, not merely under an `sbx exec` replay.
   The `su … agent` of the dispatcher (spec §14.0, "deux pièges du dispatcher") runs it as `agent`,
   and the resulting symlink is `agent:agent` — the same identity `sbx exec` reports. The one place
   this measurement could have been right and the conclusion still wrong is closed.
2. **The link phase is FIRST and the freshness command LAST**, exactly as `LinkCommand`'s contract
   claims (`000-cmd.sh` then `001-cmd.sh`).
3. **A11 holds, in both directions.** `den_link` passed its `[ ! -e "$src" ]` test on the **host**
   path of the mounted directory, and `known_hosts` — created on the host before the spawn — came
   back out of `ls -A /home/agent/.ssh` inside the VM. §14.1 already listed A11 as closed since
   2026-07-29; it is the comment in `internal/agent/links.go` that still called it "still
   unverified", and that comment is corrected in this change. The missing-source refusal stays:
   it covers a host path that disappears between create and boot, which A11 says nothing about.

## 4. Teardown

Five throwaway sandboxes created (`den-probe-57-shell`, `den-probe-57-claude`, `den-probe-57-devx`,
`den-probe-57-godev`, and `probe` via `den spawn`), **all five removed** — the four with
`sbx rm --force`, `probe` with `den rm`. `sbx ls --json` afterwards lists exactly the two sandboxes
that were there before: `dg-op-inscription`, `swimspot`. No image was created and none was removed;
`sbx template ls --json` is unchanged.

## What this smoke settles for #57

The premise is **falsified**: there is no `/home/agent/.ssh` at all. Both branches of work the issue
anticipated evaporate — the message naming the "the image put files there" case has no case to name,
and nobody has to decide whether `ssh.mode: mount` may treat a directory of image defaults as empty.
That second question was the one that would have weakened fail-closed; it is moot, not deferred.

## What this smoke does NOT say

- **It is not a re-relevé of v0.37.1.** §14.0 is attested against v0.35.0 and stays that way. This
  run exercised `create` (with `--name` and `--template`), `exec`, `rm --force`, `ls --json` and
  `template ls --json` on v0.37.1 with no visible divergence from what §14.0 records. Every other
  command is unmeasured on this version. The full re-relevé is now **due**, and is its own job.
- **It is not a claim about images that do not exist on this machine.** Four images, this machine,
  2026-08-10. An image built elsewhere that seeds `/home/agent/.ssh` would still meet the refusal —
  correctly, per §10.1.
- **It says nothing about host-key trust** (issue #58). A mounted `~/.ssh` reaching the VM is not
  the same question as what the VM trusts.
