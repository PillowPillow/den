### 1.10 `ssh -L` — not exercised end to end, and why

`sshd` is off on this machine (`ssh -o BatchMode=yes localhost true` → `ssh: connect to host
localhost port 22: Connection refused`), which is the macOS default. The line den prints is a
courtesy for a **third machine** reaching this host's loopback; exercising it would have required
turning on Remote Login, a system-configuration change outside the bench. Not done deliberately.

What *was* verified: the line's form and its arithmetic. `you` and `$(hostname)` are emitted
literally (den never resolves them), and the port is the window base, moving with the window
(`ssh -L 9500:…` then `ssh -L 11350:…`, `ssh -L 11360:…`). See **D6** for the defect this surfaced.

Distinct and worth noting: sbx v0.35.0 has its **own** `sbx ssh setup`, which provisions
`~/.ssh/config` so `ssh <sandbox>.sbx` routes through `sandboxd`. That is SSH *into* the sandbox, not
the host tunnel §8 describes. **Not run** — it writes to the user's real `~/.ssh/config`.

## 4. `--agent` — and what becomes of `CLAUDE_CONFIG_DIR` (A11)

`defaults.agent: claude`; `den beta -i --agent shell` selects the global `shell` profile, which is
neither the default agent nor the nest's own `agents.claude:` override. From inside the VM:

```
CCD=/…/scratchpad/bench/denhome/agents/shell
SMOKE=shell
MARKER-SHELL-GLOBAL
```

`sbx ls --json` mounted `.../agents/shell`, not `.../agents/claude` nor `.../agents/claude-beta`.

**A11 is closed, and twice.** A marker file written on the host *before* the spawn is readable inside
the VM at `$CLAUDE_CONFIG_DIR` — the host path IS the in-VM path — for the default profile
(`MARKER-CLAUDE-GLOBAL` on `alpha`) and for the `--agent`-selected one (`MARKER-SHELL-GLOBAL` on
`beta`). A profile carrying credentials would therefore be found, not recreated.

**Not tested: that no fresh `/login` is triggered.** Proving it needs an already-authenticated
profile, and the only one on this machine is the user's real `~/.claude`, which the bench rules
exclude from being mounted. What is proven is the mechanism the absence of `/login` depends on.

`den nest show beta` resolves the per-nest override correctly on the non-`--agent` path
(`config_dir: …/agents/claude-beta`), read from configuration, not from a VM.

## 6. Stopped sandbox — the reprise (F2) works, the ports path does not

`sbx` stops idle sandboxes **fast**: measured at roughly 45 s of inactivity (running at 17:47:58,
stopped at 17:48:51 with nothing in between). This is the normal state of a `--detach` VM, not an
edge case.

**What works.** `den sh alpha` and `den alpha` both take a stopped sandbox back, with the **same
sandbox id** (`bf6b187e-…` before and after) — no recreation:

```
$ den alpha --detach          # on a stopped sandbox
sandbox alpha stopped: it restarts on attach (its state is preserved)
waiting for network policy (3 host(s))...
sandbox alpha ready (detached) — run `den sh alpha` to enter
```

Also worth recording: `sbx policy check network --sandbox alpha` answers on a **stopped** sandbox —
the settle-loop above ran to completion against one.

**What does not.** See D2 and D3 below. And a trap for anyone reading `sbx ports`: while a sandbox is
stopped it answers `No published ports`, yet the publications **come back on resume** (9500-9502 were
listed again after the restart). That surface cannot be used to decide what a sandbox publishes
unless it is running.

In-VM *processes* do not survive: the HTTP server started before the stop was gone after it, and the
host ports answered `Connection reset by peer` until it was restarted.

Each is filed as its own GitHub issue, as F1→F6 were.

Ordering suggestion: **D1 and D2 first** — they are the two that make `den ports` unusable as a
repeated command, and they share a fix surface (`sbx ports <sandbox>` / the `ports` field of `sbx ls
--json`). **D3 goes with D2**, same decision. **D4** next: it is the only one that silently defeats a
guarantee the spec calls non-negotiable. **D5** is a spec arbitration, and belongs with #4. D6, D7
last.

### D1 — `den ports` re-run shifts the window every time and stacks up host publications

§1.7. Four runs on one sandbox, one nest, nothing else on the host → four windows, twelve host
ports for three declared ports, all live at once. The tenth run fails outright (`no free window
after 10 shifts`).

Cause, from `internal/ports/ports.go`: `windowIsFree` probes the host, and den's own previous
publication is what makes the canonical block busy. The code already documents this
(`internal/cli/ports.go:241-264` names "an earlier `den ports` run of THIS sandbox" as a candidate
holder), so it is deliberate — but the consequence is that the ordinary act of re-reading the table
destroys the bookmarkable URL §8 exists to provide, and grows the publication set without bound.

den now has the means to tell its own publications apart, which it did not when this was written:
`sbx ports <sandbox>` and the new `ports` array of `sbx ls --json` (§10) both name what *this*
sandbox already publishes.

### D2 — `den ports` on a stopped sandbox fails with an sbx 500 that names nothing actionable

```
$ sbx stop beta && sbx ls --json | grep status
      "status": "stopped",
$ den ports beta --add 9607:8080
den: sbx ports beta --publish 127.0.0.1:9607:8080: ERROR: publish ports: publish ports: request
failed: 500 Internal Server Error: request[0]: failed to resolve endpoint: no container endpoint
with IP address found
```

`Sandbox.CheckAttachable` accepts `stopped` since F2 — correctly, because `sbx exec` restarts a
stopped sandbox transparently. **`sbx ports --publish` does not.** den's shared guard therefore lets
`den ports` through into a call that cannot succeed, and the user gets an internal-server-error
string that mentions neither the sandbox's state nor `den sh <name>`.

Two ways out, both measured as available: refuse early on `IsStopped()` with a remedy, or wake the
sandbox first (a bare `sbx exec <name> true` restarts it in ~2 s — used repeatedly in this smoke).

### D3 — `den <nest> --detach` calls a stopped sandbox "ready"

Same run as above:

```
sandbox alpha stopped: it restarts on attach (its state is preserved)
waiting for network policy (3 host(s))...
sandbox alpha ready (detached) — run `den sh alpha` to enter
$ sbx ls --json | grep status
      "status": "stopped",
```

`internal/spawn/spawn.go:459-462` prints "ready (detached)" unconditionally after the settle-loop.
On the attach branch of a stopped sandbox nothing restarts it, so "ready" is false at the moment it
is printed, and any scripted follow-up — `den ports` first among them — walks straight into D2.

### D4 — den declares the sandbox ready ~35 s before the agent-freshness gate has run

`den alpha --detach` returned at 17:34:25 (7.6 s wall clock). The mixin's startup command was still
running at 17:34:54 and only completed between then and 17:35:07:

```
=== dispatcher run 2026-07-31T15:34:24Z ===
> /etc/durable-startup.d/001-startup-claude/000-cmd.sh
ok …
> /etc/durable-startup.d/001-startup-shell/000-cmd.sh
ok …
> /etc/durable-startup.d/002-startup-den-alpha/000-cmd.sh      ← still running at 17:34:54
agent claude: up to date
ok /etc/durable-startup.d/002-startup-den-alpha/000-cmd.sh
=== dispatcher complete ===
```

§9.1 says "a sandbox never starts with a stale agent" and makes the freshness command fail-closed.
den waits for the network policy (`policy.Settle`) but for nothing in the kit dispatcher: it neither
waits for `002-startup-den-*` nor reads `/var/log/sbx-kit-startup.log`. Had `claude update` failed
its three attempts, den would already have printed "ready" and handed over a shell, and the
fail-closed design would have protected nothing the user could see. It succeeded here; the race is
the finding.

### D5 — `loopback_lock`'s enforcement has no entry point; the marker is display-only

§8 promises a `loopback_lock` port is "refused outside loopback even if forced". The refusal lives at
`internal/ports/ports.go:268`, behind `Options.HostIP` — and **no CLI path ever sets that field**:
`newPortsCmd` builds `ports.Options{Extra: extra}` and nothing else (`grep -rn HostIP internal/`
returns only `internal/ports/ports.go`). The one non-loopback thing a user can type,
`--add 0.0.0.0:H:C`, is rejected earlier by `ParseAdd`, with a message that never mentions the lock:

```
$ den ports alpha --add 0.0.0.0:9600:8081
den: --add "0.0.0.0:9600:8081": 0.0.0.0 is not a bind address den offers — den publishes on
127.0.0.1 and nothing else (spec §8) …
```

The behaviour is safe (den binds loopback, always, verified by `lsof`). What is wrong is the claim:
the branch is unreachable, and §8 describes a guard the v1 CLI cannot exercise.

### D6 — the `ssh -L` line is printed unconditionally, including where it cannot work

Every windowed `den ports` run ends with `remote?  ssh -L <base>:127.0.0.1:<base> you@$(hostname)`.
On this machine, and on macOS by default, there is no SSH server listening — the command is a dead
end and nothing says so. Nor does it say that the `sshd` in question is the **host's** (den's own
machine, acting as a server for a third party), which is easy to confuse with sbx's own
`sbx ssh setup` / `ssh <sandbox>.sbx` path into the sandbox.

### D7 — every `--add` row is named `added`

```
  NAME   CONTAINER  URL
  added  8080       http://127.0.0.1:9601
  added  3000       http://127.0.0.1:9602
```

The NAME column stops distinguishing rows as soon as there is more than one `--add`. Cosmetic, same

## 8. F5, re-measured — smoke #1's statement is too strong and must not be copied into the docs

Smoke #1 concluded that a global `local-policy` allowing 197 hosts makes `egress:` "document intent
rather than constrain anything". **That is not what this machine does.** A host outside both the
nest's `egress:` and the global list is denied:

```
$ sbx policy check network --sandbox gamma --json example.com
{
  "allowed": false,
  "context": "sandbox:gamma",
  "deny_kind": "implicit",
  "reason": "No matching allow rule (default deny)",
  "target": "example.com:443",
  …
}
exit=1
```

while a host in the global list is allowed even though the nest never declared it:

```
$ sbx policy check network --sandbox gamma --json pypi.org
{ "allowed": true, "context": "sandbox:gamma", "target": "pypi.org:443", … }
exit=0
```

The 197 rules are a curated default set, not a wildcard:

```
$ sbx policy inspect local-policy
default-package-managers      56 rules
default-cloud-infrastructure  35
default-code-and-containers   33
default-cert-validation       30
default-ai-services           22
default-os-packages           16
default-fs-read-allow-all      1
default-fs-write-allow-all     1
```

Many entries are wildcards (`**.github.com:443`, `**.amazonaws.com:443`, `**.googleapis.com:443`,
`**.docker.io:443`), so the effective allowance is broad — but finite, and default-deny below it.

**The accurate sentence, for the README and the spec:** a nest's `egress:` is a **widening** of the
machine's policy, never a narrowing. den cannot make a sandbox *less* connected than the host's
`local-policy` already permits (197 rules, including filesystem read and write allow-all), and on
this machine that baseline already covers most package registries, cloud endpoints and AI services.
What `egress:` genuinely buys is access to anything *outside* that baseline — a project database at
`10.22.11.54:27017`, an internal host — and that part is enforced, as `example.com` shows.

Also observed: the per-sandbox kit policy carries **four** allows where den's mixin declares three.

```
$ sbx policy inspect 5f4ceb1d-…            # applies to sandbox:gamma
allow  api.anthropic.com    network  kit:gamma
allow  github.com           network  kit:gamma
allow  openrouter.ai        network  kit:gamma
allow  registry.npmjs.org   network  kit:gamma
```

`openrouter.ai` is **not** in den's generated `cache/mixins/gamma/spec.yaml` (checked: three entries
exactly). sbx adds it. Harmless, but it means `sbx policy inspect` is not a mirror of den's mixin,
and drift detection must not be built on the difference.

### 9.2 The real refusal text — the §14.1 quote is wrong in its second half

Raw, attributing the sentence to `sbx` and not to den's envelope:

```
$ sbx create --name densmoke-ghost --template denghost:v1 shell /…/repos/repo-a
(stdout empty)
(stderr) ERROR: request failed: 403 Forbidden: pull failed for image "denghost:v1"
exit=1
```

Through den, on a nest whose stack was never built:

```
$ den nobuild --detach
(stdout) creating sandbox nobuild (image denghost:v1)...
(stderr) den: creating sandbox nobuild: sbx create --name nobuild --template denghost:v1 --kit
<den_home>/cache/mixins/nobuild shell <repo> <den_home>/agents/claude: ERROR: request failed: 403
Forbidden: pull failed for image "denghost:v1"
exit=1
```

No sandbox husk is left behind (`sbx ls --json` → `{"sandboxes":[]}` after both).

§14.1 predicted `template "devx:v1" not found`; the real answer is a **403 Forbidden pull failure**,
because sbx treats an unknown template as a registry pull of an unqualified name. Two consequences
for #8: the message the user actually sees blames authorization, not a missing build; and den cannot
pattern-match "not found" to decide whether to suggest `den build`. With §9.1 available, it should
not try — check `sbx template ls` *before* `sbx create`, which is also the only way to say "run
`den build <stack>`" instead of relaying a 403.

Both §14.1 criticisms of den's own envelope stand and are now confirmed against a real binary: the
message does not say what to do, and it inlines the full `sbx create` argv before reaching the cause.

### §14.0 — the attested surface needs a new survey

The 2026-07-28 list is materially incomplete, and one of its notes is wrong. From `sbx --help` on
v0.35.0 (`sbx version` → `sbx version: v0.35.0 01e0152…`; **there is no `--version` flag**):

```
completion  cp  create  daemon  diagnose  exec  help  kit  login  logout  ls  policy
ports  reset  rm  run  secret  setup  ssh  stop  template  tui  version
```

- **`stop`, `secret`, `login`, `template` are in BASE sbx**, not added by `sbx-devbox` as §14.0
  states. `inspect` is not a top-level command at all; it is `sbx policy inspect`.
- **`sbx template {ls,save,rm,load}`**, `ls` with `--json` — schema in §9.1 above.
- **`sbx ls --json` now carries a `ports` array** that the 2026-07-28 schema does not mention:
  `{"host_ip","host_port","sandbox_port","protocol"}`. It appears only when the sandbox publishes.
- **`sbx policy` has more than `check`**: `allow`, `deny`, `init`, `inspect`, `log`, `ls`
  (`--wide`), `profile`, `reset`. `sbx policy inspect <policy-id|policy-name|rule-id|rule-name>`
  lists every resource with its decision.
- **`sbx ssh setup`** provisions `~/.ssh/config` with a `Host *.sbx` block routing through
  `sandboxd`. Not run — it writes to the user's real file.
- **Failure shapes of `sbx ports --publish`**: `500 Internal Server Error: … no container endpoint
  with IP address found` on a stopped sandbox; `409 Conflict: … failed to bind host port
  127.0.0.1:<P>: address already in use` when the host port is taken (names the port).
- **Failure shape of `sbx create` on an unknown template**: `403 Forbidden: pull failed for image
  "<image>"`, on stderr, exit 1, no husk.
- **`sbx exec` restarts a stopped sandbox** (`Sandbox <name> started successfully` on stderr, then
  the command runs). `sbx ports` does **not** — this asymmetry is D2.
- v0.35.0 advertises **v0.37.1** as available. Anything above should be re-surveyed.

### §8 — two drifts this smoke adds to the ones already listed in the closeout note

- The window range is **9000–17990**, not 9000–9099: `blockCount = 900` blocks of 10. §8's formula
  is right; a reader who assumes a four-digit port is not. (`gamma` landed on 11340.)
- §8's sample table writes `ws://` for the CDP row. den writes `http://` on every row, deliberately
  (`internal/cli/ports.go:308-313`). The sample should follow the code, or the divergence should be
  stated.

## Scope of this smoke

**Covered with execution evidence:** the whole of §1 except the SSH tunnel end to end; `--only` /
`--without` read from `sbx ls --json`; `-i` with a real tty and both refusals; `--agent` and
`CLAUDE_CONFIG_DIR` in the VM; interactive `den sh`; the stopped-sandbox reprise; F5 re-measured;
both #8 probes.

**Deliberately not covered, with the reason:**

- **`ssh -L` end to end** — needs `sshd` on this host (macOS default: off). Turning on Remote Login
  is a system-configuration change outside the bench. Form and arithmetic verified instead (§1.10).
- **`sbx ssh setup`** — writes to the user's real `~/.ssh/config`.
- **"no fresh `/login`"** — needs an authenticated agent profile; the only one on this machine is the
  user's real `~/.claude`, which the bench excludes. The mechanism it depends on (A11) is proven
  (§4).
- **`den build` (#8)** — not implemented. Its two blocking probes are in §9.

**Not covered, and still open for the next smoke:**

1. **A5 / A6 / A7 / A9** — the settle-loop's failure behaviour. Needs a provoked failure: a
   cancellation mid-pass (`^C` during `waiting for network policy`), a nest with ~20 egress hosts to
   see whether the 60 s budget is really respected, a `policy check` against a sandbox destroyed
   mid-loop. All four are about what den does when `sbx` misbehaves, and none of it is reachable by
   using den normally.
2. **The 10-shift exhaustion path** — `den ports` after ten runs should refuse with
   `no free window after 10 shifts (tried …)`. Reachable in ten commands on one VM; not run here
   because D1 makes it a consequence rather than an independent case. Worth confirming once D1 is
   decided, since fixing D1 may delete this path.
3. **`ports.base` validation against a real bind** — the 1024/`maxBase` and alignment refusals are
   pure computation and were not exercised.
4. **A nest declaring more than 10 ports**, and a nest whose declared ports collide with a real
   long-lived host listener. Noted in passing: this machine has PhpStorm on `*:9000` and `*:9003`,
   so a nest hashing to base 9000 would shift on every run of every instance — the D1 accumulation
   would then be permanent rather than self-inflicted.
5. **`--keep-worktrees`**, and `den rm` refusing a dirty worktree without `--force` — smoke #1
   covered the refusal path; neither was re-run here.
6. **Kit `commands.startup` on a RESUME** (F2's remaining reserve). Partially answered: the
   dispatcher **does** re-run on a fresh boot (two `=== dispatcher run … ===` entries, one baked into
   the image at 2026-07-27, one at this spawn). Whether it re-runs when a *stopped* sandbox is
   restarted by `sbx exec` was not isolated — every restart in this smoke followed a stop den had not
   caused, and the log was not read immediately after one.
7. **A second agent under `--agent` that is a real, distinct AI CLI** (codex). Only `shell` was used,
   with a no-op `update`, so the freshness path was exercised for `claude` alone.
8. **`sbx ls --json`'s new `ports` field as a den input** — D1's likely fix depends on it, and its
   behaviour on a stopped sandbox (§6: publications hidden, then restored) needs a survey of its own
   before den relies on it.
