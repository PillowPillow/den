# den V2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rewrite den on branch `v2` so that `den up`, `up -w`, `shell`, `ls`, `exec`, `rm` and `build` drive sbx through generated `sbxenv.yaml` files, and convert the `am` and `dg` environments to a base image plus kits.

**Architecture:** den reads a strict `den.yaml` (global under `~/.den/`, or in a project folder), resolves one nest, creates the worktrees, and writes three kinds of files: the `sbxenv.yaml` of the instance (in the run dir), and den-owned kits and `.git` files (in `~/.den/gen/`, outside every mount). sbx does the rest (`sbx env create`, `sbx run --name`, `sbx exec`, `sbx env rm`, `sbx template save`). A local registry under `~/.den/state/v2/` records what den created, so `ls` and `rm` replay it.

**Tech Stack:** Go 1.26, cobra, `gopkg.in/yaml.v3` (strict), `golang.org/x/mod/semver`, `charmbracelet/huh` (through `internal/prompt`), Taskfile (`task check`). sbx v0.53.0.

**Spec:** `docs/superpowers/specs/2026-11-12-den-v2-scope-design.md` (French). The validation record `docs/superpowers/specs/2026-11-12-den-v2-scope-validation.md` wins over it on any conflict. Spike results: `docs/superpowers/specs/2026-11-12-den-v2-spikes.md`. Out of scope: lots L1–L5.

## Decisions this plan rests on

Settled before this plan (do not reopen): S1, S2, S3 option (d), S4 (spikes doc, "Synthèse").

Settled by the user on 2026-11-12, during planning:

- **P1.** `den up` attaches **Claude**: `sbx run --name <instance> --workdir <start>`. `den shell` is the way to get `bash -l`.
- **P2.** The profile reaches every Claude launch: den mounts the profile directory read-only at `/den/profile`; the `den-claude` entrypoint passes `--settings /den/profile/settings.json`; the kit also installs `/etc/profile.d/den-claude.sh`, a shell function that adds the same flags to a `claude` typed in a login shell. `den exec <nest> -- claude …` runs no shell and does not get the function.

Chosen by the planner (reversible; named here so the reviewer can reject them):

- **P3. Coexistence with v1 on `~/.den`.** V2 uses only paths that v1 never reads or writes: `den.yaml`, `profiles/`, `run/`, `gen/`, `build/`, `state/v2/`, and the default worktree root `wt/`. Base image tags end in `:v2` (`pillow:v2`, `digitaleo:v2`). v1 keeps `config.yaml`, `state/sandboxes/`, `worktrees/`, `trash/`, `pillow:v1`, `digitaleo:v1`.
- **P4. dg lives on a branch.** The dg conversion goes on a new branch `den-v2` of the `den-env` repo, in a clone outside `~/.den/sources/`. v1 users fast-forward the default branch of `~/.den/sources/dg`; a V2 layout there would break their next `den source update`.
- **P5. `rm` keeps the dirty-worktree refusal.** B4 removes the trash, so the v1 `dirtyFiles` verdict becomes the only safety net. `den rm` refuses a worktree with modified, untracked or ignored files unless `--force`.
- **P6. Bases carry default kits and network.** A base declares `kits:` and `network.allow:` that every nest on that base receives before its own, plus `build.network.allow:` for the build VM only. The 10 dg nests share one base; without this, each nest repeats the same 30 network lines.
- **P7. Layers.** A nest may list extra `sbxenv.yaml` files (`layers:`), stacked after den's generated file. This is how a nest reaches sbx fields den does not model (`secrets:`, `mcp:`, `sandboxOptions.memory`). den never parses them. A layer under a mounted directory (project folder, repo, worktree) is refused: a VM could rewrite it, and sbx would act on it at the next `create` or `rm`.
- **P8. `den up` without a nest name is refused**, as in v1 (`up <nest>`). The message lists the nests den can see.
- **P9. Host commands are never run by den.** Every `sbx env create` and `sbx env rm` that den runs passes `--force --skip-host-commands`. `--force` approves the whole env plan; `--skip-host-commands` makes sure that plan never runs a `lifecycle:` command or a command-backed MCP server that a VM could have written. den declares no host command itself.
- **P10. The workspace is the run dir**, except when `start: .` (the project folder root), where it is the project folder. The project folder (with `den.yaml`, kits, provision scripts) is then out of reach of every VM that does not need it.
- **P11. `den-claude` pins its image digest.** A base without `from:` builds on that pinned image, so every `den build` starts from the same Claude Code. The converted bases end with a `claude update` step (v1 `agents.claude.update`). Alternative left open: a tag of `docker.io/sbx/claude` (unverified that one exists).

## Global Constraints

- sbx floor: `sbx.MinVersion = "v0.53.0"`. `den up`, `den exec` and `den build` check it once, before their first side effect.
- Strict YAML everywhere: `config.DecodeYAMLStrict` (`KnownFields(true)`); an unknown key is a load error that names the file.
- Refuse before the first side effect: every refusal a command can decide from config, flags, the registry or `sbx ls` comes before the first worktree, file or sbx call that changes state.
- den never deletes what it did not create: `den rm` acts only on an instance with a readable V2 record, and removes only worktrees the record marks as den-created.
- `rm` never leaves an orphan VM: the VM goes first after the refusals; the record goes last.
- den reads nothing back from a run dir. The only files in a run dir are the `sbxenv.yaml` stack; den writes them and never parses them again (S4).
- `sbx env create` and `sbx env rm` always get `--force --skip-host-commands` (P9); every sbx call den makes in `exec`, `create` and `rm` gets the global `--no-input`.
- Default worktree root: `<denHome>/wt`, layout `central`. Per-nest override allowed (B17).
- den locks every worktree it creates: `git worktree lock --reason den <path>` (S1).
- Every den sandbox composes v1/v2 kits only; the agent is `den-claude` (S3).
- Names: config file `den.yaml`; project run dir `<project>/.den/run/<instance>/`; global run dir `<denHome>/run/<instance>/`; den-owned generated files `<denHome>/gen/`; registry `<denHome>/state/v2/`.
- No test calls `t.Parallel()`, opens a socket, or spawns a process other than git. Packages that run real git call `worktree.NeutralizeGitEnvironment()` in `TestMain`.
- Goldens live in `internal/*/testdata/*.golden` and are edited by hand; there is no `-update` flag.
- Code, comments and user-facing messages in English. Errors name the file to fix and the remedy.
- Comments: a "why" at the decision site, one line where possible, no change narration.
- `task check` (lint » typecheck » test, `-count=1`, gofmt enforced) passes before every commit.
- Exclude `.claude/worktrees/` from every grep.
- Never copy values from `~/.den/config.yaml` or `~/.den/source-config/` (password, user names, internal host names) into this repo. Reference those files by path.

## Review Focus

1. **`den rm` on a worktree with work in it.** Modified, untracked, or ignored files (a `.env`) → refusal that names the files and `--force`; nothing removed, VM included. Test in Task 11.
2. **A VM-writable file reaches sbx.** A `layers:` entry under the project folder or a repo → refusal before the first side effect; and no `env create`/`env rm` call ever lacks `--skip-host-commands`. Tests in Tasks 7, 8 and 11.
3. **A sandbox with the instance name already exists, but den V2 has no record** (the v1 VM `am` before cutover). → `den up am` refuses, names `sbx rm am` and v1's `den rm am`, and creates nothing. Test in Task 8.
4. **Second `den up am -w feat`** after the first one locked the worktrees → attach, no "already locked" error. Test in Tasks 2 and 8.
5. **`den exec` never prompts.** `-i` refused; sbx always gets `--no-input`. Test in Task 9.

```go
type Repo struct { Name, Path string; Optional bool }   // Name = filepath.Base(Path)
type Resolved struct {
    Name     string
    File     *config.Loaded     // the file that declares the nest
    BaseName string
    Base     config.Base
    Profile  string
    Repos    []Repo             // declaration order
    Kits     []string           // base kits, then nest kits
    Allow    []string           // global, base, nest — de-duplicated, first occurrence kept
    Env      map[string]string  // global, then nest (nest wins on the same key)
    Ports    []config.Port
    Start    string

    Layers   []string
    Warnings []string           // e.g. an optional repo dropped for an unmapped key
}
func Find(denHome, cwd, name string) (file, global *config.Loaded, err error)
func FindBase(denHome, cwd, name string) (config.Base, *config.Loaded, error) // project file from cwd, then global
func Claim(denHome string, f *config.Loaded) error
func Resolve(denHome string, global, file *config.Loaded, name string) (*Resolved, error)
type Selection struct { Only, Without []string; Interactive bool }
func Select(ctx context.Context, r *Resolved, s Selection, p prompt.Prompter) ([]Repo, error)
```

- `Find` order: the project file found from `cwd` (if it declares `name`) → the index entry `name` (if that file still declares it) → the global file → error `unknown nest %q; nests den can see: a, b (from <files>)`. `Find` calls `Claim` on every file it loads.
- `Claim` keeps `<denHome>/state/v2/nests.yaml` (`nests: {<name>: <abs file path>}`, strict). For each nest of `f`: an entry pointing at another file that still exists and still declares the nest → error `nest %q is declared by both %s and %s; rename one`. A stale entry (file gone, or nest no longer in it) is replaced. Writes the index atomically (temp file + rename).
- `Resolve`: base looked up in `file`, then `global`; missing → error naming both files. Repo `key` resolved through `global.File.Repos`; a missing key on a required repo → error naming `GlobalFile` and the key; on an optional repo → the repo is dropped with a warning returned in `Resolved` (`Warnings []string`). Two repos with the same `Name` → error (the `/den-git/<name>` mount and `start: <repo>` need a unique name).
- `Select`: v1 semantics. `Only`/`Without` name optional repos only (naming a required repo or an unknown name → error listing the optional ones); `Only` and `Without` together → error; `Interactive` → `p.MultiSelect` over the optional repos, all preselected. No flag → every repo.
