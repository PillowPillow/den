# Compatibilité sbx v0.48.0 — design

Date : 2026-10-13. Issue : aucune. sbx installé : `v0.48.0 5caf923e0587d376848f6f388eca3e0f5ca00e2d`.
Fiche de validation : `2026-10-13-sbx-0.48-compat-validation.md` (elle gagne sur ce document).
Rapport d'écart : https://claude.ai/artifact/C8JPf5AbcR9n5Lrtm2D4pP (privé).

## 0. Résumé

Entre v0.43.0 (dernier relevé, spec principale §14.3) et v0.48.0, sbx a publié cinq versions
stables : v0.45.0, v0.45.1, v0.46.0, v0.47.0, v0.48.0. **Il n'existe pas de v0.44.x** (tags de
`docker/sbx-releases`, relevés le 2026-10-13). v0.48.0 refond toute la CLI (`--format
table|json|yaml`, listes JSON nues, champs snake_case, résultats sur stdout et le reste sur
stderr). den v1.12.0 casse à trois endroits :

| # | Changement sbx | Depuis | Effet sur den v1.12.0 | Décision |
|---|---|---|---|---|
| 1 | `sbx ls --json` rend `[...]` au lieu de `{"sandboxes":[...]}` | v0.48.0 | `sbx.Ls` refuse : `den ls`, `up`, `run`, `exec`, `shell`, `rm`, `ports` et la ligne orphelins de `doctor` meurent | décodage de la liste nue seule ; l'ancienne forme est reconnue pour être refusée avec remède |
| 2 | `sbx template ls --json` rend `[...]` au lieu de `{"images":[...]}` | v0.48.0 | `sbx.Templates` refuse : `den build` et le contrôle d'image du spawn meurent | idem |
| 3 | `sbx version` imprime `sbx version v0.48.0 …`, sans deux-points | v0.48.0 | `ParseVersion` rend `""` : `den doctor` avertit au lieu de juger, `requires.sbx` d'une source devient un avertissement | les deux écritures sont lues |

**Plancher : den exige sbx ≥ v0.48.0.** Un seul juge, `den doctor`, comme depuis le 2026-09-16.
den ne garde aucune compatibilité avec v0.47.0 et antérieur (choix HITL du 2026-10-13).

Hors périmètre, nommés pour ne pas y revenir : §7.

## 1. Relevé du 2026-10-13 — sbx v0.48.0

Mesuré dans cette session sur cette machine (darwin 25.6.0, arm64), client et serveur v0.48.0,
`api_version 0.40.0`. Sondes en lecture seule, plus deux sondes à effet de bord défaites
ensuite : un identifiant de registre jetable (`den-probe.invalid`), et des montages à chaud sur la
sandbox `am`, avec l'accord de l'utilisateur. Ce relevé sera recopié tel quel en **§14.4** de la
spec principale à l'implémentation.

### 1.1 Formes JSON

- `sbx ls --json` : liste nue. Clés d'une ligne arrêtée : `name id agent status last_used_at
  workspaces created_at`. Le champ `detached` annoncé par les notes de version **n'apparaît pas**
  sur une sandbox arrêtée ; non relevé sur une sandbox en marche. den ignore les champs inconnus.
- `sbx template ls --json` : liste nue. Clés : `id repository tag flavor created_at size`.
- `sbx policy ls SANDBOX --json` et `sbx policy ls --type network --source local --decision allow
  --json` : **inchangés**, toujours `{"rules":[…]}`, avec `scope`, `resource_type`, `decision`,
  `status` (`active`), `resources`.
- `sbx policy check network --sandbox S --json HOST` : **inchangé**, `allowed` booléen au premier
  niveau.
- `sbx secret ls -g --json` : **inchangé**, `secrets[]`, `custom_secrets[]` (`env`, `targets`),
  `shadowed_services[]`, `env_only_count`.
- `sbx inspect SANDBOX --json` : `state`, `workspace` (chaîne), `additional_workspaces[].dir`,
  `runtime_mounts[]` (`host_path`, `container_target`, `read_only` présent seulement quand vrai),
  plus `agent image kits network network_policy ports proxy secrets sessions uptime`. den ne le
  lit pas. `inspect` n'est pas listé par `sbx --help`.

### 1.2 Version

- `sbx version` : `sbx version v0.48.0 5caf923…`. Jusqu'à v0.47.0 : `sbx version: v0.47.0 …`.
- `sbx version --json` : `{client:{version,revision,build_tags}, server:{state,version,revision,
  api_version}}`. Il interroge le démon.

### 1.3 Drapeaux

- `sbx create` : `--name`, `--template`, `--skills`, `--kit` existent toujours ; `-q` devient
  `--no-progress` (den ne l'émet pas). `--pull` vaut désormais `never` par défaut pour un
  instantané local sauvé, donc un spawn depuis une image `den build` ne contacte plus de registre.
- `sbx run` : `--detached` est refusé, `-d` / `--detach` le remplace (den n'appelle pas `run`).
- `sbx secret set-custom --env` : **existe toujours**. Seuls `secret ls --env` et `secret rm --env`
  deviennent `--env-name` (den n'emploie ni l'un ni l'autre).
- `sbx template save SANDBOX TAG`, `sbx rm --force`, `sbx stop`, `sbx ports S --publish` :
  positionnels et drapeaux inchangés ; den ignore leur sortie.

### 1.4 Secrets

Un second `printf … | sbx secret set --all-sandboxes --registry den-probe.invalid
--password-stdin` échoue : code 1, stderr `error: registry secret already exists for
"den-probe.invalid" in scope "(global)"; rerun with -f to overwrite`. Avec `-f`, stdin toujours
redirigé, il réussit. L'identifiant jetable a été supprimé (`sbx secret rm --all-sandboxes
--registry den-probe.invalid -f`).

### 1.5 Montages à chaud (`sbx mount`) — sonde sur `am`

- `sbx mount` sur une sandbox **arrêtée** : `409 Conflict: sandbox "am" is not running`.
- Un montage à chaud **n'apparaît pas** dans `workspaces` de `sbx ls --json`. Il apparaît dans
  `runtime_mounts` de `sbx inspect --json`, y compris sandbox arrêtée.
- **Défaut sbx** : `HOST:HOST:ro` monte sur la cible `HOST` + `o`, en **lecture-écriture**
  (`virtiofs (rw,…)`). Reproduit sur deux répertoires. `HOST:ro` échoue : sbx lit l'hôte
  `HOST` + `o`. `HOST:/mnt/probe:ro` fonctionne, en lecture seule. `HOST` nu fonctionne, en
  lecture-écriture, à la même place. Hypothèse non vérifiée : le défaut se déclenche quand la cible
  existe sur l'hôte.
- Un montage à chaud **survit** à `sbx stop` puis redémarrage.
- `sbx umount SANDBOX HOST[:CTR]` le retire. `am` a été rendue dans son état initial : arrêtée,
  `workspaces` inchangés, `runtime_mounts` vide.

### 1.6 Divers

- `sbx exec` sur une sandbox arrêtée imprime `✓ sandbox am — started` sur **stderr** (stdout
  vide). En v0.43.0, la ligne `Sandbox <name> started successfully` allait sur stdout.
- **L'auto-arrêt existe toujours** : `am`, démarrée par un `sbx exec … true`, s'est arrêtée seule
  en quelques minutes entre deux sondes.
- Non mesuré : le statut que `sbx ls` donne à une sandbox qui ne répond plus ; le flux de la
  bannière de mise à jour ; l'effet de `sbx run -d --name` sur l'auto-arrêt (sonde refusée par la
  couche de permissions de la session).

## 2. Décodeurs — `internal/sbx/ls.go`, `internal/sbx/template.go`

Une seule fonction de `internal/sbx` décode une liste rendue par sbx, partagée par `Ls` et
`Templates` : deux copies de la reconnaissance de l'ancienne forme divergeraient.

1. `DecodeJSON(command, output, &raw)` dans un `json.RawMessage`. La tolérance à la bannière de
   mise à jour **reste** (fiche, ligne B3) : son flux en v0.48.0 n'est pas mesuré.
2. Premier octet significatif de `raw` :
   - `[` → décodage dans la tranche ; le littéral `null` aussi, et il donne une tranche vide,
     comme avant ;
   - `{` → **ancienne forme**, refus avec remède (fiche, ligne B1) :
     ``sbx ls: output has the pre-v0.48.0 shape — den requires sbx v0.48.0 or later; upgrade sbx,
     then check with `den doctor` `` ;
   - autre → l'erreur générique actuelle `sbx ls: unreadable JSON output (…): <sortie>`.
3. `Ls` trie par nom, comme avant. `Templates` garde l'ordre de sbx, comme avant.

La doctrine des commentaires « two-step decoding » ne change pas de sens — une forme inattendue
est une erreur, jamais une liste vide silencieuse — mais leur texte décrit l'objet enveloppant et
est réécrit. Le commentaire de `DecodeJSON` cite un relevé daté (`{"sandboxes":[ ... ]}`, sbx
v0.38.0) : il reste exact et n'est pas touché.

## 3. Plancher v0.48.0 — `internal/sbx/version.go`, `internal/cli/doctor.go`

- `MinVersion = "v0.48.0"`. Son commentaire cite cette spec et la raison : formes de `ls` et
  `template ls`, écriture de `sbx version`.
- `ParseVersion` lit `sbx version: vX` **et** `sbx version vX` (fiche, ligne B2). Ce n'est pas de la
  compatibilité : lire l'ancienne écriture permet à `den doctor` de dire « trop ancien » à un
  utilisateur de v0.47.0 au lieu de « version illisible ».
- `den doctor`, verdict `< MinVersion` :
  ``sbx <lu> is too old: den requires v0.48.0 or later — the `ls --json` and `template ls --json`
  shapes and the `sbx version` output changed in between; upgrade sbx``.
- `den doctor` reste le seul juge (fiche, ligne B4). `converge.checkCompatibility` appelle
  `ParseVersion` et en profite sans changement.
- `sbx.Machine` (`internal/sbx/machine.go`) répond `sbx version v0.48.0 abc`, `[]` pour `ls
  --json` et une liste nue pour `template ls --json`.

## 4. Secrets — aucun changement

`den source configure` n'écrit un identifiant de registre que si `sbx secret ls -g --json` ne le
liste pas (`converge/sbx.go`, `credentialDriver.Inspect`). Si sbx refuse malgré tout d'écraser un
identifiant présent (§1.4), den affiche ce refus et s'arrête (fiche, ligne B5). den ne passe pas
`-f` : écraser un identifiant que den croyait absent serait normaliser en silence un désaccord
entre den et sbx.

## 5. Tests

- Les fixtures `{"sandboxes":[…]}` et `{"images":[…]}` des tests (environ 190 occurrences, dans
  `internal/sbx`, `internal/cli`, `internal/spawn`, `internal/build`, `internal/converge`) passent à
  la liste nue par réécriture mécanique. Le nouveau décodeur refuse toute fixture oubliée : la
  suite le prouve.
- Nouveaux tests : l'ancienne forme est refusée avec le remède, pour `Ls` et `Templates` ; une
  valeur ni liste ni objet garde l'erreur générique ; `null` donne une liste vide ; `ParseVersion`
  lit les deux écritures ; `den doctor` juge v0.47.0 trop ancien et v0.48.0 suffisant.
- Les tests existants de la bannière (`DecodeJSON`) passent sur une liste nue.

- Spec principale : **§14.4 « Relevé du 2026-10-13 — sbx v0.48.0 »** reprend le §1 ci-dessus tel
  quel. Les §14.0 à §14.3 ne sont pas réécrits (docs datées).

- Notes de version v1.13.0 : den exige sbx ≥ v0.48.0 ; mettre sbx à jour avant den.

## 7. Hors périmètre

- **Auto-arrêt** (`sbx run -d --name`, capacité `long-running@1`) : reporté au chantier des kits v3.
- **Montages à chaud** (`sbx mount`) : refusés après la sonde du §1.5 (fiche, exceptions). À
  reprendre quand sbx corrige le montage en lecture seule à la même place.
- **`sbx env`** : chantier séparé, non engagé (issue #89).
- **Kits v3** : prototype dans une autre session ; le prompt de démarrage est rédigé après la
  release.
- Les autres nouveautés relevées par le rapport d'écart : `sbx inspect`, filtre `--created-via`,
  secrets appliqués sans redémarrage, `sbx kit add`, `sbx diagnose`, export de templates.
- Le retrait du filtre de la ligne `Sandbox … started successfully` dans le lecteur du journal de
  kit : `ParseKitLog` l'ignore déjà, et le retirer n'apporte rien.
