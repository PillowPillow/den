# Validation den sbx 0.48

*den · compatibilité sbx v0.48.0 · 13 oct. 2026*

Ces affirmations remplacent la relecture du design. Répondez ligne par ligne ; vos réponses sont enregistrées au fil de l'eau et je les relis depuis la session. La spec sera écrite à partir de cette fiche, jamais l'inverse.

## Contexte

sbx v0.48.0, installé le 13 octobre 2026, change le format de sortie de plusieurs commandes, et den v1.12.0 ne fonctionne plus : den ls, up, run, exec, shell, rm, ports et build échouent. Cette fiche fixe le contenu de la release corrective v1.13.0. Elle s'appuie sur le rapport d'écart den × sbx v0.48 publié le même jour (https://claude.ai/artifact/C8JPf5AbcR9n5Lrtm2D4pP). Valider toutes les lignes engage l'équipe à exiger sbx v0.48.0 de tous les utilisateurs de den et à ne rien livrer d'autre dans cette release.

## Glossaire

- **ancienne forme** : Sortie JSON de `sbx ls` et `sbx template ls` jusqu'à v0.47.0 : un objet qui enveloppe la liste (`{"sandboxes": [...]}`). Depuis v0.48.0, sbx renvoie la liste seule.
- **arrêt automatique** : sbx arrête une sandbox environ deux minutes après sa création quand aucun shell n'y est attaché. Mesuré sur v0.43.0, non remesuré sur v0.48.0.
- **kits v3** : Format de kit sbx apparu en v0.45.0. Une sandbox ne peut pas mélanger kits v2 et v3 ; sbx v0.48.0 accepte toujours les kits v2 que den génère.

## B — Mes choix par défaut

Les vrais points à trancher. Chaque ligne donne le choix retenu, puis l'alternative.

### Lecture des sorties sbx

- **B1.** den reconnaît l'ancienne forme dans `sbx ls` et `sbx template ls` sans la lire : il refuse avec un message dédié (sbx est antérieur à v0.48.0, mettez-le à jour, puis vérifiez avec `den doctor`). *(Design §1, décodeurs)* — _Jamais discuté_
  - Sinon : Pas de message dédié : l'ancienne forme tombe dans l'erreur générique « unreadable JSON output », sans remède.
  - **Réponse : Choix retenu**
- **B2.** den lit l'ancienne écriture de `sbx version` (`sbx version: v0.47.0`) et la nouvelle (`sbx version v0.48.0`), pour que `den doctor` dise « trop ancien » à un utilisateur de sbx v0.47.0. *(Design §2, plancher sbx)* — _Jamais discuté_
  - Sinon : den ne lit que la nouvelle écriture ; sur sbx v0.47.0, `den doctor` dit « version illisible » au lieu de « trop ancien ».
  - **Réponse : Choix retenu**
- **B3.** den garde sa tolérance à la bannière de mise à jour, bien que le plancher passe à v0.48.0. *(R4)* — _Jamais discuté_
  - Sinon : Supprimer cette tolérance maintenant, sur la foi des notes de version v0.48.0 qui envoient avertissements, conseils et progression vers la sortie d'erreur.
  - **Réponse : Choix retenu**
### Plancher sbx

- **B4.** `den doctor` reste la seule commande qui vérifie le plancher sbx ; les autres commandes ne lancent pas `sbx version` avant de travailler. *(Design §2, plancher sbx)*
  - Sinon : Chaque commande qui appelle sbx vérifie d'abord sa version et refuse en dessous du plancher.
  - **Réponse : Choix retenu**
### Secrets

- **B5.** Aucun changement de code pour `den source configure` quand une source déclare un identifiant de pull pour un registre d'images (`sbx secret set --registry`). den l'écrit déjà seulement si `sbx secret ls` ne le liste pas ; si sbx refuse quand même d'écraser un identifiant présent (observé sur v0.48.0), den affiche ce refus et s'arrête. *(R1)* — _Jamais discuté_
  - Sinon : den ajoute `-f` à `sbx secret set --registry` et écrase l'identifiant que sbx connaît déjà.
  - **Réponse : Choix retenu**
### Périmètre

- **B6.** v1.13.0 n'utilise aucune des nouveautés de sbx relevées par le rapport d'écart : ajout à chaud des montages (`sbx mount`), `sbx inspect`, filtre `--created-via` des règles réseau, secrets appliqués sans redémarrage, `sbx kit add`, `sbx diagnose`, export de templates. *(Design, hors périmètre)*
  - Sinon : Ajouter à v1.13.0 l'ajout à chaud des montages manquants lors d'une ré-attache.
  - **Réponse : L'alternative**
### Documentation

- **B7.** La release s'accompagne d'une spec dédiée en français, d'une section §14.4 « relevé sbx v0.48.0 » dans la spec principale, et d'une mise à jour de CLAUDE.md. *(Design §4, documentation)*
  - Sinon : Pas de spec dédiée : seulement la section §14.4 et CLAUDE.md.
  - **Réponse : Choix retenu**

## C — Ce que vous n'avez pas à valider

Faits mesurés sur cette machine le 13 octobre 2026, fichiers touchés et stratégie de tests. Si un de ces points contredit A ou B, c'est A ou B qui gagne.

**Mesuré sur sbx v0.48.0**

- `sbx ls --json` et `sbx template ls --json` renvoient une liste nue ; den v1.12.0 échoue avec `cannot unmarshal array`.
- `sbx version` imprime `sbx version v0.48.0 …` sans deux-points ; `den doctor` affiche `"" is not a version`.
- Inchangés : `policy ls --json` (clé `rules`, champ `status`), `policy check --json` (`allowed`), `secret ls -g --json` (`secrets`, `custom_secrets`), les drapeaux de `create` que den passe, `secret set-custom --env`.
- Un second `secret set --registry … --password-stdin` sur un hôte déjà présent échoue (code 1, `rerun with -f to overwrite`) ; avec `-f` il réussit. den n'écrit ce secret que si sa lecture de `secret ls` le dit absent.

**Non mesuré**

- Le statut qu'affiche `sbx ls` pour une sandbox qui ne répond plus.
- Le champ `detached` annoncé par les notes de version, absent sur une sandbox arrêtée.
- Le flux de la bannière de mise à jour en v0.48.0.
- L'effet de `sbx run -d --name` sur l'arrêt automatique : la sonde a été refusée par la couche de permissions.

**Fichiers et tests**

- `internal/sbx/ls.go`, `internal/sbx/template.go`, `internal/sbx/version.go`, `internal/sbx/machine.go`, `internal/cli/doctor.go`.
- Environ 190 fixtures de test passent de l'ancienne forme à la liste nue par réécriture mécanique ; le nouveau décodeur refuse toute fixture oubliée, la suite le prouve.
- Tests ajoutés : ancienne forme refusée avec remède, pour `ls` et `template ls` ; les deux écritures de `sbx version` ; v0.47.0 jugée trop ancienne par `den doctor`.
