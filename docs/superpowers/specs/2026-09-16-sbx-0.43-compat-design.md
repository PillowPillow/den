# Compatibilité sbx v0.43.0 — design

Date : 2026-09-16. Issue : #96. sbx installé : `v0.43.0 79805a6e3c6667520dc2da4f6bdeddae9b700969`.

## 0. Résumé

Entre v0.39.0 (dernier relevé, spec principale §14.2) et v0.43.0, sbx a publié trois versions
stables : v0.42.0, v0.42.1, v0.43.0. **Il n'existe ni v0.40.x ni v0.41.x** (tags de
`docker/sbx-releases`, relevés le 2026-09-16). Sur toute cette plage, den casse à deux endroits,
et trois surfaces nouvelles valent d'être prises :

| # | Changement sbx | Depuis | Effet sur den | Décision |
|---|---|---|---|---|
| 1 | Nom de sandbox : ≤ 63 octets, dernier caractère alphanumérique, `default` réservé | v0.43.0 | den construit des noms que `sbx create` refuse **après** la création du worktree (#96) | règles ajoutées à `sbx.SandboxName` |
| 2 | `sbx ports --publish` sans protocole publie en `tcp4` | v0.42.0 | `den ports` ne reconnaît plus ses propres publications (filtre `== "tcp"`) | filtre tolérant `tcp` / `tcp4` |
| 3 | `--skills=off\|readonly\|readwrite`, défaut `readonly` : montage du magasin de skills de l'hôte dans `~/.claude/skills` | v0.43.0 | deux sources de skills dans la VM, le profil den n'est plus la seule | `--skills off` sur chaque `create` |
| 4 | `sbx ls --json` porte `last_used_at` | v0.43.0 | la colonne « âge » abandonnée au §5 devient faisable | colonne `LAST USED` relative |
| 5 | `sbx secret ls --json` | v0.42.0 | l'analyseur de tableau texte de converge devient inutile | remplacé, analyseur supprimé |
| 6 | L'assistant `sbx setup` ne s'ouvre plus tout seul | v0.42.0 | le blocage `den exec -T` du CLAUDE.md n'existe plus | doc réécrite, aucun code |

**Plancher : den exige sbx ≥ v0.43.0.** Un seul juge, `den doctor`. Les autres commandes
supposent la surface v0.43.0 et laissent sbx parler s'il est trop vieux. Choix HITL du
2026-09-16 : « doctor only ».

Hors périmètre, nommés pour ne pas y revenir : `sbx version --json` dans doctor, `sbx prune`,
`--kit-arg`, et une fumée `den build` sous le nouveau défaut de consentement des credentials
(v0.43.0 : « Credential-binding consent defaults to decline » — non mesuré).

## 1. Relevé du 2026-09-16 — sbx v0.43.0

Mesuré par la session `den-probe` sur cette machine (darwin 25.6.0, arm64), client et serveur
v0.43.0, `api_version 0.31.0`. Sandbox jetable `den-probe-ok` créée avec `--skills=off` sur
`docker.io/library/godev:v1`, détruite ensuite. Ce relevé sera recopié tel quel en **§14.3** de
la spec principale à l'implémentation, qui reste le seul endroit disant ce qu'un `sbx` réel a
répondu.

### 1.1 Règles de nommage — toutes refusées AVANT l'étape image

Chaque refus imprime la ligne d'erreur et rien d'autre : ni `── RESOLVE SETUP`, ni
`✓ image ready`. Aucun worktree, aucune VM.

| Nom | Résultat |
|---|---|
| 63 caractères (`a` + 62×`b`) | **accepté** |
| 64 caractères | `ERROR: sandbox name cannot exceed 63 characters: abbb…` |
| `den-probe-` | `ERROR: sandbox name must end with an alphanumeric character: den-probe-` |
| `den-probe.` | `ERROR: sandbox name must end with an alphanumeric character: den-probe.` |
| `default` | `ERROR: sandbox name cannot be 'default'` |
| `a` + 61×`b` + `é` (63 runes, 64 octets) | `ERROR: sandbox name cannot exceed 63 characters: …` |
| `denéprobe` | `ERROR: name must match regexp ^[a-zA-Z0-9][a-zA-Z0-9.-]+$: denéprobe` |

La limite compte des **octets**. Conséquence inerte pour den : la charset est ASCII, donc
octets et runes coïncident pour tout nom que den peut construire — `len()` suffit. Ordre observé
des règles : longueur → charset → dernier caractère → `default`. Le `--help` de v0.43.0 ne
documente ni la limite ni la règle du dernier caractère ; il documente `'default' is reserved`.
Le texte d'aide a déjà été faux une fois (v0.39.0 a corrigé les signes `+`) : la mesure prime.

### 1.2 Ports — le protocole n'est PAS normalisé

Sur `swimspot` (arrêtée) :

```
$ sbx ports swimspot --publish 127.0.0.1:19876:8080
Sandbox swimspot started successfully
Published 127.0.0.1:19876 -> 8080/tcp4
$ sbx ports swimspot --publish 127.0.0.1:19877:8081/tcp
Published 127.0.0.1:19877 -> 8081/tcp
```

`sbx ls --json`, tableau `ports` :

```json
[
  { "host_ip": "127.0.0.1", "host_port": 19876, "sandbox_port": 8080, "protocol": "tcp4" },
  { "host_ip": "127.0.0.1", "host_port": 19877, "sandbox_port": 8081, "protocol": "tcp" }
]
```

Sans protocole → `"tcp4"` ; `/tcp` explicite → `"tcp"`. Deux chaînes distinctes pour deux
publications que `sbx unpublish` sans protocole retire toutes les deux. `host_port` et
`sandbox_port` sont des nombres. **`sbx ports --publish` démarre lui-même une sandbox
arrêtée** (`Sandbox swimspot started successfully` sur la sortie) — la phrase contraire dans le
commentaire de `wakeForPorts` est fausse depuis v0.42.0. `sbx ports SANDBOX --json` rend un
**tableau nu** (`[]` sans publication), là où `sbx ls --json` **omet la clé `ports`** sur une
sandbox en marche sans publication (ni `null`, ni `[]`). L'unpublish répond `Unpublish requested
for …` : aucune borne de latence mesurée. den ne dépublie jamais.

### 1.3 Assistant `setup` — le blocage §14.2 n'existe plus pour `sbx exec`

Le binaire v0.43.0 ne contient plus ni `first-run-import` ni `offeredAt` (0 occurrence, contrôle
positif `sandbox name cannot be 'default'` = 1). Le marqueur est désormais
`~/Library/Application Support/com.docker.sandboxes/sandboxes/first-login.json`, clé
`firstLoginAt`. Le fichier `first-run-import.json` encore présent sur cette machine est un
résidu.

Mesure sous pty réel (Python `pty.fork()`, stdin ET stdout tty — la condition exacte de
`spawn.LooksInteractive`), marqueur `first-login.json` retiré puis restauré à l'octet près :

| Condition | `sbx exec den-probe-ok true` | sortie | marqueur réécrit |
|---|---|---|---|
| marqueur présent (base) | 0,57 s, exit 0 | 0 octet | — |
| marqueur absent | 0,57 s, exit 0 | 0 octet, zéro ESC | **non** |

Delta de `sandboxd/daemon.log` : 25 074 octets, aucune ligne `first.?login|wizard|prompt|approv|
import|tui`. **`sbx exec` n'est pas gardé par le marqueur.** Portée : `sbx exec` seulement ; le
binaire porte `[y/N]` et `asking about host commands` à côté des chaînes `first-login`, donc
`sbx run` consulte probablement encore ce marqueur — non mesuré, et den n'appelle jamais
`sbx run`. Le blocage `den exec -T` / `den run -T` du CLAUDE.md est donc clos pour tous les
chemins de den.

BSD `script` ne sait pas allouer un pty depuis un stdin socket (`tcgetattr/ioctl: Operation not
supported on socket`) : le premier essai n'a rien mesuré. Retenir `pty.fork()` pour toute sonde
d'`isTerminal`.

### 1.4 Formes JSON et divers

- `sbx ls --json`, sandbox en marche sans publication : clés `name id agent status last_used_at
  workspaces`. `last_used_at` est RFC 3339 UTC à **partie fractionnaire variable, parfois
  absente** : `2026-09-16T11:54:16.62029Z`, `2026-09-16T12:02:36.154909Z`,
  `2026-08-24T07:34:45Z`. Un analyseur à gabarit fixe casse ; `time.Parse(time.RFC3339, …)`
  accepte les trois.
- `sbx secret ls --json` : objet à quatre clés. `secrets[]` = `scope type name secret` ;
  `custom_secrets[]` = `scope targets[] env placeholder secret` ; `shadowed_services[]` ;
  `env_only_count`. `type` vu : `service`, `registry`. `scope` vu : `global`. `secret` et
  `placeholder` portent des formes masquées (préfixe + 4 derniers caractères) : den ne les
  décode pas. Le drapeau `-g` existe toujours.
- `sbx version --json` : `{client:{version,revision,build_tags}, server:{state,version,revision,
  api_version}}`, versions préfixées `v`. `sbx version` nu : `sbx version: v0.43.0 <sha>`,
  inchangé, sans démarrage du démon (v0.43.0).
- `sbx inspect --json` : `state` (et non `status`), `workspace` chaîne (et non `workspaces`),
  `uptime` humanisé. den ne le lit pas.
- `/var/log/sbx-kit-startup.log` existe toujours. Il est **append-only à travers les runs**, et
  le premier bloc `=== dispatcher run …` date du build du template (2026-08-04). Un agent `shell`
  exécute aussi les scripts `001-startup-claude`. `ParseKitLog` ne lit que le dernier run : OK.
- **`sbx exec` imprime `Sandbox <name> started successfully` sur stdout** quand il redémarre une
  sandbox arrêtée, avant la sortie de la commande. Absent si la sandbox tournait. `ParseKitLog`
  ignore toute ligne qui n'est ni annonce `> ` ni verdict : OK. Aucun autre lecteur d'`exec`
  n'analyse la sortie.
- **Auto-arrêt en moins de 2 minutes** après `create` (run dispatcher à 11:52:12Z, redémarrage
  par `exec` à 11:54:14Z, sans action entre les deux), reproduit deux fois. Seuil non mesuré.
  La branche attach de den lit le statut dans `sbx ls --json` et `exec` redémarre : rien à
  changer, la fenêtre entre la lecture et l'attache est juste plus courte.
- `--skills=off` : `~/.claude/skills` existe dans l'image (root, `drwxr-xr-t`, vide) et
  `mount | grep -i skill` ne rend rien. Sa présence ne prouve donc pas un montage.
- `SANDBOX_NAME` et `SANDBOX_VM_ID` = nom, `SANDBOX_ID` = UUID.
- `sbx rm --force` sur une sandbox en marche réussit sans `stop` préalable.
- `sbx start` n'existe pas ; `sbx exec -T` n'existe pas. den n'appelle ni l'un ni l'autre.

### 1.5 Sans effet sur den, vérifié

`shareSkills` → `skills` dans `sbxenv.yaml` ; renommage des secrets MCP ; signature et cache des
kits git ; héritage `extends:` (aucun kit den ne l'utilise) ; standardisation des messages
d'erreur (den ne fait aucune correspondance sur le texte de sbx) ; `--kit` réservé aux mixins
(tous les kits de `~/.den` et de la source `dg` sont `kind: mixin`) ; volume Docker 10 Go ;
mémoire minimale 512 MiB (den n'a pas de bouton ressources) ; `sbx create` sans PATH (den passe
toujours au moins un workspace, garde conservée).

## 2. Règles de nom — `internal/sbx/name.go`

`SandboxName` gagne trois vérifications **sur le nom assemblé**, après le plancher
`MinNameLength` existant et pour la même raison : ce sont des règles de nom entier, pas de
composant.

```go
const MaxNameLength = 63          // MEASURED 2026-09-16, sbx v0.43.0 — octets
const ReservedName  = "default"   // idem
```

1. `len(name) > MaxNameLength` → refus. Le message donne le compte et les deux sorties :
   raccourcir le nest, ou nommer l'instance avec `--as <label court>` (un `-w` sur une branche
   longue est le cas typique : `feature/JIRA-12345-…`).
2. Dernier octet hors `alphanumericChars` → refus, en citant la règle sbx (`must end with an
   alphanumeric character`). Atteignable par `-w fix-` (git accepte une branche finissant par
   `-`, refuse `/` et `.` en fin — donc pas de `.` final possible, et un `api.` non canonique est
   déjà pris par `ValidateSandboxName`). **Pas de rognage dans `FlattenSandboxComponent`** : den
   refuse plutôt que normaliser en silence (spec §2), et rogner rendrait `fix-` et `fix`
   indiscernables.
3. `name == ReservedName` → refus. `api.default` reste légal : seul le nom entier est réservé.

Ordre dans la fonction : composants → plancher → plafond → dernier caractère → réservé. Le
`build` passe par `sbx.ValidateSandboxName` → `SandboxName` (`internal/build/sandbox.go`), donc
une seule implémentation couvre `den up`, `den run` et `den build`.

Tests (`internal/sbx/name_test.go`) : 63 accepté, 64 refusé avec le compte dans le message,
`fix-` refusé, `default` refusé, `api.default` accepté. `internal/spawn/spawn_test.go` : un
`den up api -w <branche de 70 caractères>` refuse **sans** créer de worktree et **sans** appeler
sbx (le double n'enregistre aucun appel) — c'est l'invariant §6 que #96 signale.

## 3. `--skills off` — `internal/sbx/argv.go`, `internal/build/sandbox.go`

Deux jetons `"--skills", "off"`, placés juste après `--template`, dans les deux constructeurs.
Commentaire au point de décision : le défaut v0.43.0 (`readonly`, ou `skills.defaultMode`)
monte le magasin de l'hôte en lecture seule dans `~/.claude/skills` ; den pointe l'agent sur son
profil par `CLAUDE_CONFIG_DIR`, donc pas de collision de chemin, mais deux sources de skills
dans une VM contredisent le rôle du profil (mémoire « den agent profile carries skills »).
Mesuré : `--skills=off` ne monte rien. Le build reçoit le même drapeau : une image capturée
n'inclut pas les montages, mais l'argv de den doit dire la même chose partout.

Tests : `argv_test.go`, `sandbox_test.go`, et le golden
`internal/build/testdata/sequence-two-stacks.golden`, édité à la main.

## 4. Ports — `internal/cli/ports.go`, `internal/sbx/ls.go`

`publicationsOf` garde une publication si `host_ip == ports.Loopback` **et** `protocol ∈ {tcp,
tcp4}`. `PublishSpec` reste sans suffixe : den ne lie qu'en IPv4 sur 127.0.0.1 (spec §8), et
`tcp4` est exactement cela. Accepter aussi `tcp` : les publications faites avant v0.42.0
reviennent au resume avec leur chaîne d'origine.

Doc de `sbx.Publication` : enregistre les deux chaînes et leur non-normalisation, avec la date.
`wakeForPorts` : l'`exec true` reste — den doit lire les publications existantes **sur une VM en
marche** avant de publier, sinon il republie une fenêtre déjà liée — et le commentaire perd la
phrase « `sbx ports` (unlike `sbx exec`) does not restart one », fausse depuis v0.42.0. Le
message utilisateur de `wakeForPorts` est réécrit dans le même sens.

Tests : `internal/cli/ports_test.go` — une publication `tcp4` sur `127.0.0.1` est reconnue comme
celle de den et n'est pas republiée ; une `tcp6` ou une autre adresse reste ignorée.

## 5. Plancher v0.43.0 — `internal/sbx/version.go`, `internal/cli/doctor.go`

`internal/sbx` prend en charge la version, parce qu'il possède le concept (règle « fix at the
owning layer ») :

```go
const MinVersion = "v0.43.0"
func ParseVersion(output string) string   // déplacé de converge.ParseSbxVersion, même contrat
func Version(ctx, r Runner) (string, error) // `sbx version` nu — aucun démarrage du démon
```

`converge.ParseSbxVersion` disparaît, `converge/service.go` appelle `sbx.ParseVersion`. La
comparaison est `golang.org/x/mod/semver`, déjà dans `go.mod` et déjà employé par
`source.CheckCompatibility`.

`internal/cli/doctor.go` — pas `internal/doctor`, dont la première ligne promet « no side
effects, no network » et qui n'exécute jamais sbx — ajoute une vérification `sbx version` à côté
de `networkPolicyChecks` :

| Lecture | Niveau | Détail |
|---|---|---|
| `sbx version` échoue | fail | l'erreur sbx telle quelle |
| version illisible (`dev`, format inconnu) | warn | « den cannot check the sbx floor » |
| `< v0.43.0` | fail | `sbx <lu> is too old: den requires v0.43.0 or later — sandbox names, port protocols and \`secret ls --json\` changed; upgrade sbx` |
| `≥ v0.43.0` | ok | la version lue |

Aucune autre commande ne vérifie : `up`, `run`, `build`, `ports`, `converge` supposent la
surface v0.43.0 (choix HITL). `sbx.Machine` répond désormais `sbx version: v0.43.0 abc`.

## 6. Secrets — `internal/converge/sbx.go`

`ReadSbxState` exécute `secret ls -g --json` et décode par `sbx.DecodeJSON` (bannière de mise à
jour tolérée, comme partout ailleurs) :

```go
type secretList struct {
    Secrets []struct {
        Scope, Type, Name string
    } `json:"secrets"`
    CustomSecrets []struct {
        Scope   string
        Targets []string
        Env     string
    } `json:"custom_secrets"`
}
```

`secret` et `placeholder` **n'existent pas dans la structure** : den ne garde aucun fragment de
secret en mémoire ni dans ses erreurs (doctrine inchangée). `type == "service"` → `Services`,
`"registry"` → `Registries`, autre → ignoré (sbx peut ajouter un genre). Chaque élément de
`targets` produit sa propre clé `customKey(target, env)` : le manifeste de source déclare un
`Host` par ressource (`sbx.go:301`), et une entrée sbx à plusieurs cibles doit répondre pour
chacune. Une clé `secrets` **absente** (pas seulement vide) est une erreur — même doctrine que
`Ls` et `Templates` : une liste vide dirait « rien n'est configuré » et converge proposerait de
recréer des credentials existants.

Supprimés : `parseSecretList`, ses trois tests (`TestParseSecretList…`), la garde d'en-tête,
l'appel `sbx.StripUpdateBanner` sur ce chemin, et les deux tableaux de `Machine.renderSecrets`,
qui rend la forme JSON. `TestReadSbxStateIgnoresTheUpdateBannerOnTheSecretTable` devient un test
de bannière devant du JSON.

## 7. Colonne `LAST USED` — `internal/sbx/ls.go`, `internal/cli/ls.go`, `internal/cli/root.go`

- `sbx.Sandbox` gagne `LastUsedAt string \`json:"last_used_at"\``, brut.
- `sbx.Relative(now time.Time, rfc3339 string) string` rend `-` si vide ou illisible, `<1m`
  sous la minute, puis `<n>m`, `<n>h` (≥ 60 min), `<n>d` (≥ 24 h). Entiers tronqués. Un
  horodatage dans le futur (horloge de l'hôte) rend `<1m`, jamais un négatif.
- `cli.Deps` gagne `Now func() time.Time`, nil = `time.Now`, injecté comme tout accès système ;
  `NewRootCmdWith` câble le réel, les tests figent l'instant.
- `den ls` : colonne `LAST USED` entre `STATUS` et `WORKSPACES`. Le libellé dit ce que sbx
  mesure — dernier usage, pas âge.

Tests : `sbx/ls_test.go` (les trois formats de fraction), un test table de `Relative`,
`cli/ls_test.go` avec `Now` figé.
